RSVP for the invitation: what the research found

The question: how do we let about 150 guests answer from the invitation page, and let two non-developers read the answers on their phones, for free and safely?

Short answer. The most common free pattern is a static page on GitHub Pages that saves answers to a Google Sheet through Apps Script. It is easy to read but weak on security and hard to test. The stronger pattern, and the one I lean to, is a small Cloudflare Worker with a D1 database behind the same static page, plus a private phone page for the couple. It is also free, and the free limits are about a hundred times larger than what 150 guests need.

1. How wedding sites handle RSVPs today

Commercial tools (Zola, Joy, Wedibox, Bridebook and others) offer three ways to know who is answering:

Name lookup

The guest types their name on the RSVP page and picks their household. No link to manage, but misspelled names fail, and one guest's name can reveal who else is invited.

Unique link per household

Each party gets its own link, so the form already knows who they are. This is what Bridebook offers, and what the plan here uses.

Printed code

A code on the paper invitation opens the guest's own details: seats, meal options, event access. Described by Paperlust. Same idea as our link, delivered by hand.

  • One answer per household is simpler, but partial attendance, meals and named plus-ones get harder. Several tools let any member answer for everyone.
  • Fixed seats versus open: Wedibox offers both. In invitation mode a household can never reply for more people than it was given.
  • Deadlines: at least one tool (Wedsites) shows the deadline only as a reminder and does not close the form. Closing the form on the server is a real difference.
  • Advice repeated across vendors: make it work on a phone, and have a few friends try it first.

Sizing. 150 families at a few requests each is under a thousand requests in total. The free daily limits are 100 times higher or more, so the limit that matters is not capacity but safety.

4. Spam and abuse

  • Unguessable codes are the main defence. A 12-character code has about 60 random bits. With a cap on failed attempts, guessing is not practical.
  • Cloudflare Turnstile is a free, invisible bot check. It needs a script from Cloudflare on the page and a server check of each token. It is an optional extra here, not a need, and it adds a third-party request for guests.
  • Cloudflare's Rate Limiting binding exists but its limits are approximate, per data-centre location, and only allow 10 or 60 second periods. The official page does not say whether the Free plan includes it. Exact counters in the database are simpler to test and to explain.
  • Also standard: a request size cap, strict field lengths, and cross-origin calls accepted only from the invitation's own address.

5. The personal link and what stays private

  • The part of an address after # is never sent to a server and is not part of the request that a link preview fetches. Putting the code there keeps it out of server logs and out of Referer headers.
  • Limits: the page's own JavaScript can read it, it shows in the address bar and in screenshots, and the preview behaviour of WhatsApp is not documented, so it must be checked on a real phone.
  • The database should hold only a hash of each code, so a leaked copy cannot rebuild the links.
  • A guest must only ever get their own household's record, and an unknown code must look the same as a malformed one.

6. Allergies and personal data

Several guides say that dietary needs and allergies count as health data under GDPR (Article 9), and that religious diets can reveal beliefs. None of the sources were from a regulator, and none settled whether a couple counts as a data controller, so treat this as a prompt to be careful, not as legal advice.

  • Keep the field optional and short, and say why it is asked and who sees it (a one-line notice, wording is the couple's).
  • Collect no phone, email or address. The invitation already arrives by WhatsApp.
  • Share allergy information with the caterer only, and delete the database after the event (a date is set in the plan).

7. Accessibility of the form

  • Group each yes or no question in a fieldset with a short legend, so a screen reader announces who the question is about.
  • Errors (WCAG 3.3.1, level A) must be text that says what to fix, not colour alone, and be tied to the field with aria-describedby.
  • A live region must exist before its text is inserted, or nothing is announced.
  • Inputs at 16 px or more stop iPhones from zooming in on focus.

8. WhatsApp's browser

I found no official documentation for the in-app browser of WhatsApp. On iPhone, in-app browsers are normally web views built on Safari's engine, so Safari's rules apply. One report says saved data in such web views can be missing between page loads. For us that means a draft saved on the phone is a convenience, never the proof of an answer. Only the server's confirmation counts. This has to be tested on real phones, which this machine cannot do.

9. What this means for the plan

Keeps

  • Worker + D1, site stays on GitHub Pages.
  • Code after #, only its hash stored.
  • Per person yes or no, optional diet text, one message.
  • A couple-only phone page and a CSV export.

Adjusts

  • Flood limits stay as exact database counters, no reliance on the rate-limit binding.
  • Turnstile stays off unless spam shows up.
  • Diet field gets a short purpose notice (wording is the couple's).
  • Saved drafts are treated as best effort.

10. What I could not confirm

  • Whether the Free plan includes the Rate Limiting binding (not needed by the plan).
  • Tally's current free limits and the exact current Apps Script quotas.
  • How WhatsApp's in-app browser treats storage, cross-origin calls and the # part. Needs a real phone.
  • Legal position of a couple under GDPR. Needs a professional if it matters.
  • Several comparison articles are vendor blogs. I used the official Cloudflare pages for the limits that matter.
